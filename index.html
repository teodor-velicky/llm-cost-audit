Case study · LLM cost engineering

How I cut a production LLM pipeline's cost by about 60%

The team had shipped AI features quickly and they worked. Nobody could say what each one cost, which model it ran on, or whether the bill was growing because of real usage or because of waste.

Client
A real-estate technology company running several LLM automations in production. Name under NDA; references on request.
Role
First dedicated AI consultant, part time, 2026.
Stack
PHP monolith with cron jobs, Anthropic API, some TypeScript and Python tooling.
~60%

lower cost on the highest-volume pipeline — an email classifier running on every inbound message — with identical output.

What I did

  1. 01

    Fixed the classifier

    Every classification sent the same long instructions again and re-processed emails that had already been handled. I changed it to a prime-then-fan-out pattern: one call primes the prompt cache, then seven parallel calls read from it at the cached price instead of paying full input price. I also removed a reprocess=1 flag that was pushing already-classified emails back through the model. The pipeline's cost dropped by roughly 60%. The outputs did not change.

  2. 02

    Measured the rest before changing it

    I went through every AI automation in the company and set up one way of measuring cost: Anthropic invoice data reconciled against per-call token counts times list pricing, broken down per workflow and per model. This gave the team cost per feature and caught a cache-token accounting mismatch that had been inflating the bill.

  3. 03

    Declined two changes

    With numbers in hand I evaluated moving workflows to a cheaper model, and a cascade setup where a cheap model answers first and a strong one is only called on low confidence. For this workload the quality loss and extra latency were not worth the savings. I recommended against both and wrote down the reasoning so it can be revisited when the traffic or the prices change.

  4. 04

    Put prompts in one place

    Prompts were string literals scattered across the codebase. I moved them into a prompt editor with access controls and a byte-parity check, so an edited prompt produces exactly the bytes the code used to hard-code. Product people can change wording without an engineer and without silent regressions.

  5. 05

    Made the jobs visible

    The automations ran out of a single cron.php. I split it into separate jobs and built a UI to edit cron tasks, plus an overview page showing what runs, when, and what it costs.

  6. 06

    Deleted dead AI code

    Leftovers from earlier experiments were removed so the team has less to reason about.

Result

  • Roughly 60% lower cost on the highest-volume pipeline, with identical output.
  • Per-feature and per-model cost that matches the actual invoice.
  • Two expensive changes avoided on the strength of measurement.
  • Prompts, jobs and costs editable and visible in a UI instead of buried in code.

If you run LLMs in production

The order matters: measure first, find the structural waste — caching, redundant reprocessing, fan-outs that skip the cache — fix it as merged pull requests, and only then look at model changes, with evals.
